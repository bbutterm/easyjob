# Проверка безопасности перед первым публичным развёртыванием

Сервис «Карьерный помощник», ветка `claude/new-session-cp5tel`. Проверка по чтению кода,
без изменений. Дата: 2026-09-06.

Область: `server/**`, `src/api.js`, режим сервера в `src/app.js`, `src/ui.js`,
`src/screens-core.js`, `src/screens-prep.js`, `shared/ai/**`, `deploy/**`, `.env.example`,
`.gitignore`.

Итог коротко: инъекций (SQL / HTML) и утечек ключа в ответах и журнале не найдено;
разграничение доступа по сессии выдержано на всех маршрутах. Главная проблема — все три
механизма ограничения частоты и стоимости обходятся тривиально, что для публичного
сервиса с платной моделью опасно. Есть также клиентская уязвимость через неочищенные
идентификаторы из ответа модели и пробелы в заголовках безопасности nginx.

---

## Состояние исправлений

Все критичные и важные находки исправлены в тот же день, на каждую добавлена регрессия
в `tests/server.test.js` (раздел «Регрессии по проверке безопасности»).

| Находка | Что сделано |
| --- | --- |
| C1 | Путь нормализуется один раз, проверка лимитов и выбор маршрута идут по одному значению. Регрессия отправляет сырой запрос с `/../` через сокет |
| C2 | Дневной лимит подготовок считается и по сессии, и по хэшу адреса; новые сессии с одного адреса ограничены в час; страница отдаётся без создания сессии |
| C3 | Берётся `X-Real-IP` от nginx, иначе последний элемент `X-Forwarded-For`; nginx выставляет `X-Real-IP` |
| I1 | Идентификаторы из ответа модели и ключи ответов проверяются по белому списку символов и запрету `__proto__`, `constructor`, `prototype`; `setPath` на клиенте отклоняет те же имена |
| I2 | `DELETE /api/me` удаляет всё немедленно и сбрасывает cookie; кнопка в настройках в режиме сервера |
| I3 | CSP, `X-Frame-Options: DENY`, `Referrer-Policy`, `nosniff` на странице и в nginx; HSTS в nginx закомментирован до включения HTTPS |
| I4 | `engines.node >= 22.5` — версия, где появился встроенный SQLite |

Раздел «Желательно» не трогался. Ниже — исходный отчёт.

## Критично (чинить до запуска)

### C1. Ограничитель дорогих запросов к модели обходится через `/../` в пути

- Где: `server/index.js:23` (регэксп `EXPENSIVE`), `server/index.js:114`
  (`EXPENSIVE.test(req.url.split('?')[0])`), `server/lib/router.js:63`
  (`new URL(req.url, ...).pathname` — маршрут ищется по нормализованному пути).
- Что не так: маршрутизатор сопоставляет запрос по **нормализованному** `url.pathname`
  (Node сам сворачивает `.`/`..` и декодирует `%2e`), а проверка «дорогой ли это маршрут»
  в `handle()` выполняется по **сырому** `req.url`. Пути с сегментом `/../` доходят до
  нужного обработчика, но не совпадают с `EXPENSIVE`, поэтому лимит по сессии
  (`RATE_LIMIT_EXPENSIVE_PER_MINUTE`, по умолчанию 12/мин) к ним не применяется.
- Как эксплуатировать: со своей валидной сессией и своим `prep`
  `POST /api/preps/x/../<PREP_ID>/questions` (или `/rebuild`, `/card`, `/interviews`).
  Проверено: `new URL('/api/preps/x/../y/questions','http://localhost').pathname`
  → `/api/preps/y/questions` (маршрут срабатывает), а `EXPENSIVE.test('/api/preps/x/../y/questions')`
  → `false`. Модель вызывается без строгого лимита — до общего лимита по IP (120/мин),
  то есть в 10 раз выше задуманного.
- Чем грозит: неконтролируемые платные вызовы провайдера, разгон себестоимости, отказ
  в обслуживании по бюджету.
- Что делать: проверять принадлежность к дорогим маршрутам по нормализованному
  `new URL(req.url,...).pathname`, а не по `req.url`. Ещё лучше — навесить дорогой лимит
  внутри самих обработчиков (после `dispatch`), где путь уже разобран, а не по строке URL.

### C2. Лимиты по сессии обходятся сбросом cookie (новая сессия — новый лимит)

- Где: `server/lib/session.js:40-52` (`resolve` создаёт новую сессию при отсутствующей или
  неверной cookie), `server/index.js:116` (дорогой лимит ключуется по `current.id`),
  `server/routes/api.js:18-23,173-178` (лимит бесплатных подготовок считает
  `db.preps.countToday(sid)` по сессии).
- Что не так: и дорогой лимит по сессии, и лимит `FREE_PREPS_PER_DAY` привязаны к
  идентификатору сессии. Клиент, который не присылает cookie, каждый раз получает новую
  сессию (и новую запись в таблице `sessions`), а значит — обнулённые счётчики.
- Как эксплуатировать: скрипт шлёт запросы без заголовка `Cookie`. Каждый запрос создаёт
  новую сессию → лимит модели и лимит подготовок в день не действуют. Дополнительно —
  неограниченный рост таблицы `sessions` (записи удаляются только по неактивности через
  `DATA_RETENTION_DAYS`).
- Чем грозит: обход платного лимита, разгон затрат на модель, раздувание базы.
- Что делать: считать создание сессии дорогим и лимитировать его по адресу; либо не
  создавать сессию для запросов, приходящих без валидной cookie к защищённым маршрутам
  (возвращать 401/загрузку страницы), а учёт лимитов вести не только по сессии, но и по
  адресу клиента.

### C3. Ограничитель по IP обходится подделкой `X-Forwarded-For` при `TRUST_PROXY=1`

- Где: `server/lib/ratelimit.js:45-51` (`clientAddress` берёт **левое** значение
  `X-Forwarded-For.split(',')[0]`), `server/index.js:44` (`secure`/доверие прокси из
  `TRUST_PROXY`), `server/index.js:103`.
- Что не так: за nginx `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`
  (`deploy/nginx.conf:18`) **дописывает** реальный адрес клиента справа к тому, что прислал
  клиент. Код же при `TRUST_PROXY=1` берёт **самое левое** значение — то есть полностью
  подконтрольное клиенту. Развёртывание за прокси требует `TRUST_PROXY=1` (см.
  `deploy/nginx.conf:6`, `docs/deploy.md`), поэтому это штатная конфигурация.
- Как эксплуатировать: слать запросы с меняющимся `X-Forwarded-For: <случайный IP>` —
  каждый запрос попадает в свою корзину лимита. Единственная защита по IP (120/мин)
  снимается полностью; в связке с C1/C2 все ограничения частоты и стоимости не работают.
- Чем грозит: перебор, злоупотребление платной моделью, DoS.
- Что делать: при одном доверенном прокси брать **последний** элемент `X-Forwarded-For`
  (адрес, добавленный самим nginx), а не первый; либо задать число доверенных прокси и
  отсчитывать адрес справа. Не доверять клиентской части заголовка.

## Важно (чинить в первую неделю)

### I1. Идентификаторы из ответа модели не очищаются → прототипное загрязнение на клиенте

- Где: `server/routes/api.js:232` (`id: q.id || ('q'+...)` — `q.id` не проходит через
  `str()`), также `server/routes/api.js:55,72` (`r.id`, `m.requirementId` — то же);
  `src/screens-prep.js:172-176` (путь состояния строится как
  `'preps.' + prepIndex(prep) + '.answers.' + q.id`); `src/app.js:26-34` (`setPath`
  делит путь по `.`), `src/app.js:1299-1300`.
- Что не так: идентификатор вопроса берётся из ответа модели без ограничения набора
  символов (в отличие от `text`/`why`/`guidance`, которые прогоняются через `str()`).
  Он подставляется в «путь модели» `data-model`, а `setPath` на клиенте делит этот путь по
  точке и идёт по объекту состояния. Точки и сегмент `__proto__` внутри `q.id` уводят
  запись в прототип. Провайдер по условию задачи недоверенный.
- Как эксплуатировать: провайдер (или влияние через текст вакансии) возвращает вопрос с
  `id = "x.__proto__.polluted"`. При вводе ответа в это поле `setPath('preps.0.answers.x.__proto__.polluted', …)`
  пишет в `Object.prototype`. Проверено локально на логике `setPath`:
  `Object.prototype.polluted` становится задан. XSS напрямую нет (значения при выводе
  экранируются через `esc`), но загрязнение прототипа портит состояние страницы и может
  служить ступенью к дальнейшим сбоям/обходам логики.
- Чем грозит: порча клиентского состояния, потенциальная эскалация.
- Что делать: на сервере пропускать `q.id`, `r.id`, `m.requirementId` через `str()` с
  жёстким белым списком символов (`[A-Za-z0-9_-]`, без точек); на клиенте в `setPath`
  отклонять сегменты `__proto__`/`prototype`/`constructor` и не собирать пути из
  недоверенных строк.

### I2. Нет способа для пользователя немедленно удалить свои данные

- Где: `server/routes/api.js` (есть `DELETE /api/resumes/:id` и `DELETE /api/preps/:id`,
  но нет удаления сессии/всех данных), `server/lib/retention.js`,
  `server/lib/db.js:142-158` (`removeInactiveSince`).
- Что не так: удалить всё, что связано с сессией, можно только автоматически по истечении
  `DATA_RETENTION_DAYS` неактивности. Пользователь не может стереть свои резюме, вакансии,
  подготовки и интервью одним действием прямо сейчас. Для сервиса, хранящего резюме
  (персональные данные), это важно и с точки зрения приватности, и юридически.
- Чем грозит: невозможность выполнить запрос на удаление, претензии по приватности.
- Что делать: добавить маршрут «удалить все мои данные» (удаляет резюме, вакансии,
  подготовки, интервью и саму сессию в одной транзакции, по образцу `removeInactiveSince`),
  вынести кнопку в раздел «Мои данные».

### I3. nginx не выставляет заголовки безопасности (HSTS, антикликджекинг, CSP)

- Где: `deploy/nginx.conf` (нет `Strict-Transport-Security`, `X-Frame-Options`/
  `Content-Security-Policy: frame-ancestors`, нет CSP).
- Что не так: сервис отдаёт `x-content-type-options` и `referrer-policy` из приложения
  (`server/index.js:79-80,98-99`), но на уровне прокси нет HSTS (защита от даунгрейда на
  http после первого https), нет защиты от встраивания в чужой iframe (кликджекинг на
  странице с резюме и действиями) и нет CSP как второго рубежа против XSS. Страница —
  один инлайновый скрипт и инлайновые стили, поэтому строгий CSP затруднён, но
  `frame-ancestors 'none'` и запрет внешних источников реализуемы.
- Чем грозит: кликджекинг, понижение до http, отсутствие подстраховки при будущей ошибке
  экранирования.
- Что делать: в блоке 443 добавить `add_header Strict-Transport-Security "max-age=63072000" always;`,
  `add_header X-Frame-Options DENY always;` и хотя бы `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'; base-uri 'none'`
  (с `'unsafe-inline'` для script/style, пока сборка инлайновая).

### I4. `node:sqlite` экспериментальный + несогласованный `engines`

- Где: `server/lib/db.js:10` (`require('node:sqlite')`), `package.json:19-21`
  (`"engines": { "node": ">=20" }`).
- Что не так: `node:sqlite` — экспериментальный модуль, появившийся в Node 22.5; API может
  меняться между версиями, гарантий стабильности и того же уровня ревью, что у зрелых
  модулей, нет. При этом `engines` разрешает Node 20, где модуля ещё нет — установка/запуск
  на Node 20 упадёт, хотя документация требует Node 22.
- Чем грозит: поломка при обновлении Node, запуск на неподдерживаемой версии.
- Что делать: поднять `engines` до фактически требуемой версии (например `>=22.5`),
  зафиксировать её в systemd/деплое; следить за статусом модуля и предусмотреть путь
  отхода (например `better-sqlite3`), понимая, что это добавит нативную зависимость.

## Желательно

- **Слабая нейтрализация инъекций в промпт.** `shared/ai/prompts.js:114-116`: `neutralize`
  обезвреживает только строку, которая целиком является заголовком в квадратных скобках
  (`^\s*\[...\]\s*$`, 1–60 символов). Заголовок с текстом на той же строке, регистр,
  иные приёмы не покрываются. Основная защита — оговорка в системном промпте
  (`prompts.js:135-137`), что содержимое разделов — данные, а не инструкции. Последствия
  ограничены: вывод экранируется, инструментов у модели нет, канал утечки данных
  отсутствует, поэтому риск низкий; стоит явно задокументировать ограничение и не полагаться
  на `neutralize` как на границу безопасности.
- **Резюме `data` — произвольный объект без схемы.** `server/routes/api.js:109-114`:
  проверяется только `rawText` (длина). Прочие поля (`experience`, `skills`, произвольные
  ключи) сохраняются как есть, возвращаются клиенту и уходят в промпт. Ограничено общим
  размером тела (512 КБ, `server/lib/router.js:7`). Стоит валидировать структуру и
  ограничить размеры массивов/число ключей `answers` (`api.js:244-249`).
- **Возможное эхо заголовков в ошибке провайдера.** `shared/ai/providers/*` возвращают
  `json.error.message` наружу; текст ошибки попадает клиенту (502) и в журнал
  (`server/lib/ai.js:133-136`). Если сервис провайдера в теле ошибки отразит присланный
  заголовок `Authorization`, это утечёт. Вероятность низкая; стоит не пробрасывать сырое
  сообщение сервиса дословно, а логировать только код/усечённый текст.
- **Пустой `SESSION_SECRET`.** `server/lib/session.js:15-17`, `server/index.js:56-59`:
  при пустом секрете генерируется случайный на процесс — подделать подпись нельзя, но при
  каждом перезапуске все сессии инвалидируются, данные пользователей «повисают». Стоит
  завершаться с ошибкой при пустом `SESSION_SECRET` в боевом режиме (сейчас — только
  предупреждение), а не только генерировать его в `docs/deploy.md`.
- **Проверка Origin пропускает запрос без заголовка.** `server/index.js:86-90`: при
  отсутствии `Origin` возвращается `true`. На практике CSRF закрыт связкой `SameSite=Lax`
  (`session.js:34`) + обязательный `application/json` (`router.js:79`) + отсутствие
  мутирующих GET, поэтому это лишь ослабление глубины защиты; можно дополнительно
  требовать совпадения `Origin`/`Referer` для мутаций.
- **Усиление systemd.** `deploy/career-assistant.service` уже неплох (`NoNewPrivileges`,
  `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `ReadWritePaths`). Стоит добавить
  `RestrictAddressFamilies=AF_INET AF_INET6`, `SystemCallFilter=@system-service`,
  `MemoryMax`/`TasksMax` (защита от DoS), а также убедиться, что права `.env` — 600
  (юнит это не гарантирует; `EnvironmentFile` при мировом чтении раскроет ключ и
  `ADMIN_TOKEN`).
- **Таймауты приёма запроса.** Явно не задаются `server.requestTimeout`/`headersTimeout`
  (`server/index.js:136`), `readBody` без своего таймаута (`router.js:26-42`). Полагается
  на значения Node по умолчанию; при публичном запуске стоит выставить их явно (защита от
  медленных клиентов).
- **`session_id` остаётся в `usage` бессрочно.** `server/lib/db.js:142-158`,
  `retention.js`: при очистке удаляются данные, но строки `usage` (с `session_id`)
  сохраняются для учёта. Содержимого там нет, это осознанное решение, но сам идентификатор
  — связующее звено; для «полного забвения» стоит обезличивать `session_id` в `usage`
  при удалении сессии.

## Проверено, проблем нет

- **XSS.** Все поля из ответа модели выводятся через `esc`/`escLines`: сопоставление
  (`screens-prep.js:73,78,79`), вопросы (`:167,170,171,186`), итог интервью
  (`:371-375`), реплики интервьюера и потоковый `partial` (`:319,324`), разбор резюме
  before/after/strengths (`screens-core.js:471-475,505,516`), карточка
  (`screens-prep.js:751-790`). `esc` экранирует `& < > " '` (`ui.js:9-16`). `note()`
  получает только статический HTML. Сырой `prep.card` из модели в HTML не вставляется.
- **SQL-инъекции.** Все запросы параметризованы; `preps.set` (`db.js:268-281`) строит
  список столбцов из белого списка `allowed`, значения — плейсхолдеры; `usage.summary`
  (`db.js:348-363`) — статический SQL с привязкой `since`.
- **Подделка/подбор сессии.** Подпись HMAC-SHA256, сверка длины + `timingSafeEqual`
  (`session.js:23-31`), идентификатор — 72 бита случайности (`db.js:110-112`).
- **Разграничение доступа.** Каждый маршрут фильтрует `WHERE ... AND session_id = ?`,
  включая `interviews`, `preps/:id/rebuild`, `answers`, `turns`, `continue`, `finish`
  (`db.js` и `routes/api.js`).
- **Админ-токен.** `timingSafeEqual` с проверкой длины (`admin.js:13-20`), маршруты
  отдают 404 при незаданном токене, находятся под лимитом по IP.
- **Секреты в ответах.** `/api/health`, `/api/me`, `/api/admin/usage` отдают
  `ai.describe()` с булевым `hasKey`, но не сам ключ и не содержимое (`ai.js:40-51`,
  `routes/api.js:86-102`, `admin.js:28-32`).
- **Раздача статики.** Отдаётся только `/` и `/index.html` (`server/index.js:71-83`);
  обхода пути к `.env`/`.git`/базе нет.
- **SSRF.** `AI_ENDPOINT` и OAuth-URL GigaChat задаются только из окружения владельца;
  пути от клиента к адресу исходящего запроса нет (`ai.js:20-33,107-124`).
- **Размер тела.** Ограничен 512 КБ в приложении (`router.js:7,32-36`) и 1 МБ в nginx.
