# План доведения до рабочего продукта

Составлен 6 сентября 2026 по итогам двух аудитов (`docs/audit-summary.md`) и семи
выполненных итераций (`docs/iterations.md`). Оценки трудозатрат взяты из технического
аудита: один разработчик с ИИ-ассистентом, погрешность ±50 %. Это план, а не обещание сроков.

## Где мы сейчас

Есть: кликабельный макет всех экранов, библиотека профессий, провайдер-нейтральный слой
запросов к модели с адаптерами для семи сервисов, слоистое хранение контекста, прототип
программы для компьютера, 171 автоматическая проверка, CI.

Нет: ни одного настоящего вызова модели, бэкенда, базы, аутентификации, платежей, чтения
файлов резюме, деплоя. Всё, что «работает», работает на заглушке.

Аудит оценивает путь до MVP без голоса и без программы для компьютера в **19–31
человеко-недель**; около 1–2 из них уже закрыты итерациями 1–5. Ниже эти недели разложены
по этапам с условиями перехода.

---

## Этап 0. Решения, без которых дальше идти нельзя

Это не работа, а выбор. Пока он не сделан, каждый следующий этап строится на догадке.

| Решение | Варианты | Рекомендация аудитов | Что блокирует |
| --- | --- | --- | --- |
| Судьба помощника на собеседовании | закрыть / заморозить / оставить только для письменных заданий | **закрыть** | тарифную сетку, юридический объём, B2B |
| Провайдер модели для данных с ПДн | YandexGPT / GigaChat / локальная модель | российский сервис | этап 1 целиком |
| Правовая форма | самозанятый / ИП | самозанятый для старта, ИП при выходе в B2B | платежи, договоры |
| Фокусные профессии | 6–8 из библиотеки | офисные не-IT + IT-джуниоры | банк вопросов, SEO-страницы |
| Фронтенд | оставить текущий / переписать на фреймворк | **переписать до подключения бэкенда** | этап 3 |

**Критерий выхода:** пять строк заполнены и записаны в этот файл.

---

## Этап 1. Первый живой вызов модели

**Срок:** 1–2 недели. **Цель:** узнать, работает ли продукт вообще, до того как строить вокруг
него инфраструктуру.

1. Получить ключ выбранного российского провайдера и прогнать четыре базовые задачи
   через `shared/ai`: разбор резюме, извлечение требований, сопоставление, вопросы.
   Первый же вызов покажет, верны ли формы запросов, которые сейчас помечены как несверенные.
2. Собрать проверочный набор: 20–30 пар «резюме + вакансия» по фокусным профессиям.
   Анонимизированные, с согласия владельцев, или составленные вручную. Без этого набора
   качество подсказок нельзя ни измерить, ни улучшить.
3. Прогнать набор, оценить ответы руками по трём критериям: не выдумывает ли модель факты,
   ссылается ли на конкретные места резюме, полезен ли совет. Записать долю провалов.
4. Замерить реальный расход токенов на одну подготовку и посчитать себестоимость. Сравнить
   с оценкой аудита (около 95 ₽ на российской модели начального уровня).
5. Переписать промпты по результатам. Повторить пункт 3.

**Критерий выхода:** на проверочном наборе не больше одного выдуманного факта на десять
разборов, себестоимость подготовки известна с точностью до рубля, формы запросов сверены.

**Стоп-сигнал:** если после двух кругов правки промптов модель выдумывает факты чаще, чем в
каждом пятом разборе, — менять модель на более сильную и пересчитывать экономику, а не
продолжать.

## Этап 2. Бэкенд и хранение

**Срок:** 4–7 недель. **Цель:** данные пользователя живут не в памяти вкладки.

1. Сервер: один процесс, одна база. Для старта достаточно SQLite или Postgres на одном
   хостинге в РФ (требование 152-ФЗ для персональных данных).
2. Прокси к модели: единственное место, где хранится ключ провайдера. Учёт токенов по
   пользователю, дневные лимиты, повторы и таймауты — уже написаны в `shared/ai`, переносятся
   как есть.
3. Сущности из `docs/context-model.md`: профиль, версии резюме, вакансии, подготовки,
   сопоставления, ответы. Версионирование резюме и отметка устаревших отчётов — по той же
   логике, что в макете.
4. Вход без пароля: ссылка на почту или код. Полноценная аутентификация с восстановлением —
   позже, когда будет что восстанавливать.
5. Журналы с редакцией персональных данных (`redactForLog` уже есть), простые оповещения об
   ошибках.
6. Черновик политики обработки данных и согласия — на просмотр юристу. Сроки хранения
   резюме, порядок удаления по запросу.

**Критерий выхода:** пользователь заходит, вставляет резюме и вакансию, получает
сопоставление от настоящей модели, закрывает браузер, возвращается — данные на месте.

## Этап 3. Фронтенд на фреймворке

**Срок:** 4–6 недель, частично параллельно этапу 2. **Цель:** основа, которую можно
развивать, вместо перерисовки всего экрана через `innerHTML`.

1. Выбрать один стек: TypeScript + Vite + Svelte или Vue. Любой из двух подходит для одного
   разработчика; React тяжелее и не даёт здесь преимуществ.
2. Переносить экраны по одному, начиная с тех, что нужны для MVP: вставка вакансии и резюме →
   сопоставление → вопросы → текстовое интервью → карточка подготовки. Мастер резюме с нуля,
   загрузка файлов, голос, помощник — не в MVP.
3. Забрать из текущего макета то, что переживает переезд: токены оформления и `styles.css`,
   доменную логику из `state.js` (устаревание, версии), тексты экранов, `shared/`.
4. Проверки Playwright перенести на новые экраны, а не переписывать с нуля.

**Критерий выхода:** MVP-путь проходит на новом фронтенде против настоящего бэкенда;
старый `index.html` остаётся как демонстрация, но больше не развивается.

## Этап 4. Публичный MVP

**Срок:** 2–3 недели. **Цель:** первые чужие люди пользуются продуктом и платят.

1. Бесплатный доступ без регистрации с лимитом: одна вакансия в день.
2. Разовая покупка через ЮKassa для самозанятого: снять лимит на 7 дней. Подписки нет, пока
   нет повторных покупок — прямая рекомендация рыночного аудита.
3. Банк вопросов: по 30–50 реальных вопросов на каждую фокусную профессию. Это ручная работа
   с форумами и отзывами о собеседованиях, её нельзя автоматизировать без потери качества.
   Аудит: банк вопросов важнее ИИ-обёртки.
4. Страницы «вопросы на собеседовании: <профессия>» для поисковиков и 2–3 статьи на
   площадках с профессиональной аудиторией. Платный трафик при разовой покупке убыточен —
   не покупать.
5. Аналитика без сторонних трекеров: свои события в свою базу. Это согласуется с обещанием
   приватности и не требует согласий на cookie.

**Критерий выхода:** продукт открыт, первая оплата прошла, себестоимость пользователя
известна по факту, а не по оценке.

---

## Этап 5. Проверка спроса и развилка

**Срок:** 4–6 недель наблюдения. **Цель:** решить, куда идти дальше, по цифрам.

Смотреть три числа: доля посетителей, дошедших до сопоставления; доля заплативших; доля
вернувшихся за второй вакансией. Пороги задать до запуска, а не после.

Три исхода:

- **Есть платящие и возвраты** → этап 6.
- **Есть интерес, нет оплат** → менять цену и момент оплаты, не функции.
- **Нет интереса** → остановиться. Рыночный аудит считает этот исход вероятным для чистого
  B2C и предлагает B2B как единственный масштабируемый путь.

---

## Этап 6. Расширение (только при подтверждённом спросе)

В порядке приоритета, по одному:

1. **Разбор после интервью.** Пользователь описывает, что спрашивали и что отвечал, — получает
   разбор и план. Дёшево, честно, продаётся B2B.
2. **Чтение PDF и DOCX.** Готовые библиотеки; качество на резюме с дизайнерской вёрсткой —
   отдельная работа. 1–2 недели базово.
3. **Голосовое интервью.** Сначала замер стоимости распознавания речи: по одному из источников
   она может быть 10–30 ₽/мин, и тогда сценарий убыточен. Без замера не начинать. 4–8 недель,
   высокая неопределённость.
4. **B2B.** Оформить ИП, предложение 3–5 карьерным центрам вузов и онлайн-школам. Требует
   продаж «ногами», а не кода.
5. **Мастер резюме с нуля** — вернуть из макета, когда будет спрос именно на него.

## Помощник на собеседовании — отдельная дорожка

Если на этапе 0 принято решение «оставить», это другой продукт со своими условиями входа,
и его нельзя вести параллельно с MVP силами одного человека:

- юридическое заключение по обработке данных третьих лиц в кадре;
- настоящий захват экрана вместо миниатюры;
- подпись кода для macOS и Windows, иначе система блокирует запуск;
- честный ответ на вопрос, зачем он нужен, если вопрос на видеособеседовании произносится
  вслух и на экране не появляется.

Оценка аудита: 4–8 недель до распространяемого состояния плюс постоянная поддержка.

Рекомендация: заморозить. Код остаётся в `desktop/`, тесты остаются в CI, раздел в макете
остаётся с пометкой. Возвращаться к нему только после этапа 5 и только при наличии
юридического заключения.

---

## Чего не делать

- Не строить бэкенд до первого живого вызова модели: можно построить инфраструктуру вокруг
  функции, которая не работает.
- Не переносить в MVP все экраны макета. Макет — карта возможностей, а не список требований.
- Не подключать подписку до повторных покупок.
- Не покупать трафик при разовой покупке.
- Не расширять список профессий до сбора банка вопросов по уже выбранным.
- Не отправлять данные с ПДн зарубежным моделям.

## Первые пять действий

1. Заполнить таблицу этапа 0 в этом файле.
2. Зарегистрироваться у выбранного провайдера, получить ключ, положить его в переменную
   окружения — не в код.
3. Написать скрипт, который прогоняет `match.requirements` на одном настоящем резюме
   и вакансии через `shared/ai`, и посмотреть на ответ глазами.
4. Найти 20 пар «резюме + вакансия» по фокусным профессиям.
5. Записать себестоимость первого вызова в рублях.

Пункты 2–5 укладываются в одну неделю и дают больше информации о судьбе продукта, чем всё
сделанное до этого.
