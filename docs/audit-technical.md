## 1. Архитектура

### Что есть

Три слабо связанных части: (а) веб-макет на глобальных IIFE-модулях, строках HTML и полной
перерисовке; (б) `shared/` — чистые модули без зависимостей с UMD-обёртками; (в) Electron с
корректным разделением main/preload/renderer. Разделение (б) от (а) и (в) — правильное
решение, и `shared/` действительно можно переносить. Одной строкой: сама идея слоёв
контекста по скорости изменения — здравая. Дальше — что с ней не так.

### Что развалится при росте

1. **Одно состояние — один глобальный объект, мутируемый отовсюду.** `Store.update(fn)`
   — это `fn(state); notify()`. Нет ни неизменяемости, ни истории, ни разделения на
   серверные и локальные данные. Как только появятся асинхронные загрузки (реальный API),
   в `Store` нет понятий «загружается / ошибка / устарело» — `scenario: 'loading'` сейчас
   глобальный флаг демо-панели, а не состояние конкретного запроса.
2. **Маршрутизация — `switch` по строке** (`app.js:50-79`) плюс отдельный список `KNOWN`
   (`:45-46`) плюс отдельная таблица секций (`:81-87`). Три места, которые надо
   синхронизировать при каждом новом экране.
3. **Диспетчер действий — один `switch` на 650 строк** (`app.js:286-949`). Уже сейчас
   в нём 90+ веток; с реальной логикой (валидация, запросы, отмена) он станет
   неподдерживаемым.
4. **Демо-данные вшиты в модель данных.** `DEMO_DATA.vacancy.requirements` клонируется в
   пользовательскую вакансию (`app.js:591`), `resume.demo: true` — поле сущности. При
   переходе на реальные данные придётся вычищать «демо» из каждой сущности и экрана.

### Frontend: строки HTML + `innerHTML` + перерисовка всего экрана — годится ли как основа?

**Нет. Это тупик для продукта, и переход на фреймворк нужен до, а не после подключения
бэкенда.** Обоснование по существу, а не «зависит»:

- **Полная перерисовка на каждое изменение** уже сейчас порождает костыли: сохранение
  фокуса по `id`, восстановление каретки, ручная прокрутка чата, `input` без перерисовки
  как исключение из правила (`app.js:986-997`). Каждая новая интерактивная деталь
  (потоковый вывод ответа модели, индикатор загрузки файла, аудио-волна, drag-and-drop
  порядка опыта) потребует нового исключения. Тост, исчезающий через 4 секунды, уже
  перерисовывает страницу, на которой пользователь печатает.
- **Безопасность на дисциплине.** API `note(kind, html)` и `modal.body` принимают
  HTML-строки. Пока данные — только пользовательские, экранирование выдерживают. Когда
  придёт текст модели с форматированием, ссылками и цитатами, потребуется либо
  собственный sanitizer, либо фреймворк, который экранирует по умолчанию.
- **Нет компонентной изоляции и типов.** 1 400 строк экранов — это функции, возвращающие
  строки. Их нельзя протестировать по отдельности, нельзя переиспользовать с другими
  данными, нельзя проверить типами. Ошибка в имени поля — тихий `undefined` в HTML.
- **Доступность страдает системно:** `aria-live` регионы пересоздаются целиком при
  каждой перерисовке → скринридер перечитывает журнал чата заново; ловушка фокуса
  навешивается заново на каждый рендер.
- **Стоимость перехода растёт.** Сейчас 2 400 строк экранов и 1 000 строк диспетчера.
  Через полгода будет 8 000, и переход станет отдельным проектом.

Что сохранить при переходе: `styles.css` (токены и компоненты — переносимы), доменную
логику `state.js` (`markStale`, `bumpResume`, `createPrep`) как чистые функции,
`professions.js` как данные, `shared/` целиком.

Рекомендация: TypeScript + Vite + React или Svelte (любой из двух; критерий — тот, на
котором владелец быстрее найдёт помощь), роутер библиотечный, состояние — простое
(Zustand/сигналы), а не Redux. Без SSR: продукт за логином, SEO не нужен.

## 2. Качество и поддерживаемость

Конкретика — в таблицах D1–D13 и I10–I14 выше. Общие наблюдения:

- **Дублирование.** Экраны повторяют один и тот же каркас: `pageHead + sourcesBar +
  staleBanner + note('demo')`; сценарные заглушки скопированы пять раз; таблицы статусов
  дважды в одной функции; проверка тарифа на двух уровнях.
- **Связанность.** `app.js` знает про внутренности каждого экрана (`ScreensPrep.ensureChat`,
  поля `chat.index`, `voice.line`). `screens-prep.js` знает про `DEMO_DATA.interviewScript`.
  Смена формата сценария затронет три файла.
- **Скрытые контракты.** `data-model` — строковый путь, разбираемый в `setPath`;
  `data-act="go:#/…"` — маршрут внутри имени действия; `data-change-act` против
  `data-act`; `confirmAct`/`confirmData` — действие внутри состояния модалки. Ни один из
  этих контрактов не проверяется.
- **Где легко посадить баг:** таймеры без отмены (`app.js:429, 741, 868`), которые
  пишут в состояние спустя секунду после того, как пользователь мог всё сбросить;
  `sourcesModalBody` пересобирает HTML модалки внутри `update` (`app.js:650`);
  `prepIndex(prep)` возвращает `0` для несуществующего (`screens-prep.js:189`) — ответы
  запишутся в чужую подготовку.
- **Нет инструментов.** Нет линтера, форматтера, типов, `package.json` в корне. Код
  написан в ES5-стиле (`var`, IIFE) при целевых браузерах, которые давно понимают модули.

## 3. Безопасность

### Веб-макет

- **XSS:** пользовательский ввод проходит через `UI.esc`/`escLines` во всех найденных
  местах (проверены `screens-core.js`, `screens-prep.js`, `app.js`, `ui.js`). Атрибуты
  `value`, `placeholder`, `data-id` — экранированы. Модалки с пользовательскими данными
  экранируют (`app.js:534`). Уязвимость не найдена. Риск структурный (I11): два API
  принимают сырой HTML; `id` и `rows` в `UI.field` (`ui.js:134, 144`) не экранируются —
  сейчас они только из кода.
- **localStorage:** читается с валидацией каждого поля (`state.js:15-36`) — правильно.
- **`setPath` по строковому пути** (`app.js:26-34`) — потенциальный prototype pollution,
  если путь когда-либо придёт не из шаблона. Сейчас — нет.
- Нет CSP и в веб-макете — для `file://` демо не критично.

### Electron

Сделано верно, одной строкой: `contextIsolation: true`, `nodeIntegration: false`,
preload с закрытым перечнем методов и allowlist каналов подписки (`preload.js:32-36`),
`shell.openExternal` только для `https://`, удалённый контент не загружается, ключ на диск
не пишется.

Что не сделано или сделано слабо:

- **Нет CSP** в трёх HTML (`renderer/*.html`), нет обработчиков `will-navigate` и
  `setWindowOpenHandler` (I13).
- **IPC не проверяет отправителя** (`main.js:170-271`): любой из трёх renderer может
  вызвать любой handler, включая `consent:accept`. Сейчас все три — свои; при появлении
  webview или внешнего контента станет дырой.
- **`settings:set` без валидации значений** (I12): `intervalSec` может прийти строкой,
  `endpoint` — любым URL, куда затем уходит ключ.
- **Ключ API:** только память процесса — честно для прототипа. `process.env.ASSISTANT_API_KEY`
  для GUI-приложения — неудобный и небезопасный путь (env виден в `ps`/Task Manager у
  дочерних процессов). Для продукта — `safeStorage` (Keychain/DPAPI) или, лучше,
  **ключа у клиента вообще не должно быть**: запросы к модели идут через ваш бэкенд с
  пользовательским токеном, лимитами и учётом расходов. Иначе один пользователь может
  выкачать бюджет всего проекта.
- **Что попадает на диск:** `settings.json` (провайдер, модель, endpoint, режим, факт и
  дата согласия). Кадры и подсказки — в памяти. Не проверено (см. раздел 11): дампы
  падений Electron/Chromium (`crashDumps`) могут содержать содержимое памяти renderer, в
  том числе data-URL миниатюр источников (`main.js:205`, до 320×180 каждый).
- **`activate` на macOS** (`main.js:138-140`) открывает панель без проверки согласия;
  `session:start` согласие проверяет (`:219`), так что обход неполный — но лишний путь.
- **`--no-sandbox`** только в тестах — правильно.

### Общий слой

- `execute()` (`providers/index.js:30-63`) — единственная точка сети. Хорошо. Но
  `fetch` без таймаута и без ограничения размера ответа. Ключ передаётся в заголовках,
  не логируется — логов нет вообще, что само по себе проблема для продукта.
- `redactForLog` не соответствует реальным именам полей (I2).

## 4. Приватность

### Веб-макет

Наружу не уходит ничего: сетевых запросов нет (`tests/check.js:410-412` это проверяет),
`localStorage` — только настройки демо. Утверждения README соответствуют коду.

### Программа для компьютера — что реально уходит

При `readMode: vision` и настоящем провайдере каждые `intervalSec` (мин. 5 с, по
умолчанию 12) уходит:

1. `screen.extract`: кадр выбранного источника целиком (по замыслу; по факту — B1),
   плюс **всё резюме, вакансия, требования, слабые места** (I1), плюс системная
   инструкция.
2. `assistant.hint` (если вопрос найден): всё то же самое без кадра, плюс найденный
   вопрос, плюс история вопросов.

Куда: на адрес из `capabilities.js` или на произвольный `endpoint` из настроек.

### Риски для данных третьих лиц

- Если источник — **экран**, а не окно, в кадр попадают: лицо и имя собеседующего
  (видеозвонок), чат, уведомления мессенджеров, соседние окна с чужими данными
  (почта, документы работодателя). Лицо — биометрические ПДн по 152-ФЗ и «особая
  категория» по GDPR; их обработка требует отдельного согласия субъекта, а не
  пользователя.
- Согласие на экране первого запуска — самодекларация пользователя. Оно защищает
  владельца продукта от претензий пользователя, но не от претензий собеседующего или
  работодателя, и не заменяет правовое основание обработки.
- Сроки хранения у провайдеров моделей: по умолчанию у провайдеров есть период
  удержания входных данных (для API Anthropic — 30 дней в стандартном режиме; условия
  ZDR требуют отдельного соглашения). Данные третьих лиц из чужого чата будут лежать у
  третьей компании за границей — трансграничная передача без основания.
- Локализация ПДн российских граждан (242-ФЗ) при провайдере вне РФ — отдельный вопрос
  к юристу, не к коду.

### Достаточно ли текущих ограничений

Нет. Ограничения текущего кода: (а) явный запуск сессии, (б) выбор источника, (в)
галочки согласия, (г) индикатор в окне. Ни одно из них не уменьшает объём чужих данных в
кадре. Что реально уменьшает:

1. Разрешить только источник типа `window`, запретить `screen` (`main.js:200-203, 287-290`).
2. Режим `text` с локальным OCR и отправкой только дельты — он спроектирован
   (`lib/ocr.js`), но не реализован; именно он должен быть единственным режимом в
   продукте. `vision` — оставить для внутренней отладки за флагом.
3. Обрезка кадра до области чата / субтитров, а не весь источник.
4. Не отправлять резюме в `screen.extract` (I1).
5. Локальное определение «изменился ли кадр» до любого запроса.

## 5. Слой LLM

### Соответствие адаптера Anthropic справочнику (сверено по актуальному описанию API)

Совпадает: идентификатор `claude-opus-5`; `system` отдельным полем; `output_config.effort`
внутри `output_config`; отсутствие prefill; обработка `stop_reason: refusal` и чтение
только `text`-блоков; заголовок `anthropic-version`.

Не совпадает с заявленным или рискует:

- **`max_tokens` 250/300** при включённом по умолчанию адаптивном рассуждении (I5).
  Либо явно управлять глубиной и поднять `max_tokens` до 1–2K, либо ожидать обрезанный
  JSON.
- **Структурированный вывод не используется** (I4), хотя это единственный надёжный способ
  получить валидный JSON; `parseJson` с поиском первой `{` — паллиатив.
- **Кэширование не используется** (I3, I4): ни `cache_control`, ни разделения на блоки.
  Один текстовый блок `userText` содержит и стабильное, и изменчивое — точку разрыва
  поставить некуда. Минимальный кэшируемый префикс у моделей — от 512 до 4 096 токенов
  в зависимости от модели; системная инструкция проекта (~250 токенов) сама по себе ниже
  порога.
- **Потоковый режим объявлен, но не реализован** (B2).
- Не обрабатываются: `stop_reason: max_tokens` (обрезка), 429/529 с `retry-after`,
  `overloaded_error`.

### Адаптеры OpenAI и Gemini

Автор честно помечает их как «не сверены». Я их по документации тоже не сверял (нет
доступа к сети в этом аудите). По коду: OpenAI использует `response_format: json_object`
вместо объявленного в профиле `json_schema`; Gemini игнорирует `streaming` вовсе (эндпоинт
`generateContent`); ни один из трёх адаптеров не имеет тестов на форму ответа с ошибкой
или на нестандартный статус.

### Жизнеспособность абстракции

Нормализованный запрос (`request.js:86-101`) — это **один system + один user + опционально
одна картинка**. Это не абстракция над чатом, это абстракция над одиночным вызовом.
Что сломается:

| Возможность | Что придётся менять |
|---|---|
| **Стриминг** | `execute()` возвращает объект; нужен async-итератор, парсер SSE на каждого провайдера (у всех три разных формата событий), обработка обрыва потока. Плюс конфликт: `assistant.hint` — JSON и стриминг одновременно; JSON нельзя показывать по мере прихода. Либо `text` для подсказки, либо стрим до конца и разбор. |
| **Tool use** | В запросе нет `tools`, нет `messages[]`, `fromWire` читает только текст. Нужны: массив сообщений с блоками, цикл `tool_use → tool_result`, схемы инструментов на каждого провайдера. Фактически новый `request.js` и переписанные адаптеры. |
| **Кэширование префикса** | Разделить `userText` на минимум два блока (стабильный/изменчивый), перенести картинку в конец, ставить `cache_control` по правилам провайдера, проверять `cache_read_input_tokens`. Порядок блоков должен быть одинаковым у всех провайдеров. |
| **Батчи** | Отдельный эндпоинт и асинхронная модель «создал задание → опросил → забрал». В `execute()` нет понятия отложенного результата. Для `resume.review` и `questions.generate` батчи дали бы −50% стоимости — но это отдельный путь, не расширение текущего. |
| **Многоходовое интервью** | `interview.turn` кладёт всю историю в текст пользователя. Провайдеры лучше работают с нативными ролями `user/assistant`; текущая форма мешает и кэшу, и качеству. |

Вывод: слой нужно переписать вокруг `messages[]` с блоками контента и результатом-потоком
до того, как на него ляжет реальная логика. Сейчас его дешевле переписать, чем расширять.
При этом «провайдер-нейтральность» как цель первого релиза — сомнительна: пока нет оценок
качества (evals), сравнить провайдеров нечем, а поддерживать три адаптера — есть чем.

### Контекстный слой

- **Оценка токенов** `length/3` (`store.js:47-51`) неверна для base64 (B1) и груба для
  кириллицы; для JSON с отступами (`prompts.js:92`, `JSON.stringify(v, null, 1)`) —
  завышена. Калибровать через `count_tokens` провайдера.
- **Бюджет долями по слоям** независимо от задачи: `screen.extract` с бюджетом 8 000
  выделяет 2 800 на `preparation`, которое ему не нужно, и 1 200 на `moment`, которое
  единственное нужно.
- **Усечение** выкидывает ключи целиком в фиксированном порядке (I7). Порядок
  `education → achievements → skills → experience` для задачи сопоставления означает, что
  при нехватке места модель получит опыт без навыков и ответит «навык не подтверждён».
- **`experience.slice(0, 1)` как «последнее место работы»** (`store.js:172`) — зависит от
  порядка массива, который нигде не гарантирован.
- **Свёртка** — конкатенация усечённых строк с обрезкой начала (`store.js:105-116`).
  Как аварийный запасной вариант — приемлемо; как основной — теряется начало интервью,
  где обычно самое важное (представление, ожидания).
- **`windowTurns`** считает реплики, а не токены; 10 длинных ответов кандидата не
  поместятся, 10 коротких вопросов займут 5% окна.

1. **`desktop.test.js` с `ASSISTANT_FAKE_CAPTURE=1` и провайдером `mock`** проверяет

2. **`docs/test-report.md`** написан вручную и утверждает «все выполнялись реально» —

3. **«Кадры не сохранены»** (`desktop.test.js:180`) проверяет по расширению файла.
   Кадр в JSON, `.bin` или в кэше Chromium не будет найден.
4. **«Нет сторонних запросов»** в веб-тесте — проверка того, чего в коде и так нет
   (нет `fetch`). Ценность будет, когда `fetch` появится.
5. **Текстовые селекторы** (`button:has-text("Далее")`) — тесты ломаются от правки
   копирайта и не ломаются от поломки логики, если текст совпал.

## 8. Риски Electron-модуля

| Риск | Блокер / решаемо | Комментарий |
|---|---|---|
| **Захват через миниатюру `getSources`** (B3) | Блокер для функции | Не захват, а превью. Переделать на `getUserMedia` + `chromeMediaSourceId` в renderer или `setDisplayMediaRequestHandler`. Заодно даёт видеопоток, из которого можно брать кадры без переперечисления всех окон каждые 12 с. |
| **macOS: разрешение «Запись экрана» (TCC)** | Решаемо, но неприятно | Без него — пустые кадры; выдаётся вручную в системных настройках; для неподписанного приложения запросы ведут себя ненадёжно; macOS 15 периодически переспрашивает. |
| **Подпись кода и нотаризация** | Обязательно, решаемо деньгами | macOS: Apple Developer + notarize, иначе Gatekeeper блокирует. Windows: сертификат OV/EV; без него SmartScreen показывает «неизвестный издатель», репутация набирается неделями. |
| **Антивирусы** | Серьёзно, решаемо частично | Неподписанное приложение, которое снимает экран, держит окно поверх всех и шлёт данные в сеть, — эвристический профиль шпионского ПО. Подпись и репутация снижают, но ложные срабатывания будут. |
| **Автообновления** | Решаемо | `electron-updater` + хостинг; требует подписи. |
| **Прозрачное окно always-on-top** | Кроссплатформенные различия, решаемо | Windows: прозрачность и `frame: false` работают, но с ограничениями (DWM, масштабирование, HDR). Linux: зависит от композитора; на Wayland `desktopCapturer` идёт через PipeWire-портал — иной UX. Тестировалось только под xvfb, что не равно ни одной реальной системе. |
| **Wayland и захват** | Решаемо | Портал спрашивает пользователя на каждый захват; `getSources` может вернуть пусто. |
| **Детектирование площадками** | Не технический блокер, но продуктовый | Zoom/Meet/Teams в браузере процессы не видят. Прокторинговые и anti-cheat системы (в тех-собеседованиях: платформы с прокторингом, корпоративные EDR) фиксируют always-on-top окна и захват экрана. Ключевое: окно **по замыслу видно при демонстрации экрана** — продукт честен, но тогда его сценарий «подсказки на живом интервью» практически нерабочий: собеседующий увидит подсказки при первом «поделитесь экраном». Это противоречие в требованиях, а не в коде. |
| **Mac App Store** | Блокер для этого канала | Песочница MAS не пропускает захват чужих окон. Только прямое распространение. |
| **Размер и ресурсы** | Приемлемо | ~200 МБ на платформу; enumerate источников каждые 12 с — заметная нагрузка на слабых машинах. |
| **Локальный OCR** | Решаемо, дорого | Tesseract (wasm или нативный) + языковые данные, +50–100 МБ; качество на скриншотах чата с кириллицей требует предобработки. Без него — только `vision`, со всеми рисками раздела 4. |

Вывод по модулю: как прототип «может ли Electron показать окно и снять кадр» — да.
До распространяемого продукта — B3 + подпись + разрешения + OCR + правовая рамка. И до
всего этого — решение, есть ли у функции «подсказки на живом собеседовании» право на
существование в продукте, который вы готовы защищать перед работодателями и
регулятором.

## 9. Стоимость эксплуатации

Точные цены брать из прайс-листа провайдера на день расчёта; ниже — ориентиры на
основе кэшированного справочника (июнь 2026): `claude-opus-5` — 5 $/M вход, 25 $/M выход;
`claude-sonnet-5` — 2 $/10 $; `claude-haiku-4-5` — 1 $/5 $. Оценки объёмов — грубые,
из размеров текущих промптов и типичных резюме (2–4 К токенов) и вакансий (1–2 К).

### Структура расчёта

```
стоимость_задачи = вход_токены × цена_входа + выход_токены × цена_выхода
стоимость_подготовки = Σ задач (review, parse, match, questions) + N_ходов × turn + summary
стоимость_пользователя_в_месяц = подготовок × стоимость_подготовки + интервью × стоимость_интервью
```

### Веб-сценарий, одна подготовка

| Задача | Вход, тыс. токенов | Выход | Opus 5 | Sonnet 5 |
|---|---|---|---|---|
| `resume.review` | 3–5 | 1–2 | 0,04–0,08 $ | 0,02–0,03 $ |
| `vacancy.parse` | 2–3 | 0,5–1 | 0,02–0,04 $ | 0,01 $ |
| `match.requirements` | 4–6 | 1–2 | 0,05–0,08 $ | 0,02–0,03 $ |
| `questions.generate` | 4–6 | 1–2 | 0,05–0,08 $ | 0,02–0,03 $ |
| Текстовое интервью: 10 ходов × (6–10 К вход, 0,3 К выход) + итог | 70–110 | 5 | 0,5–0,7 $ | 0,2–0,3 $ |
| **Итого за подготовку с одним интервью** | ~90–130 | ~10 | **~0,7–1,0 $** | **~0,3–0,4 $** |

Пользователь с 3 подготовками и 3 интервью в месяц: ~2–3 $ на Opus, ~1 $ на Sonnet,
**без** кэширования. С кэшированием префикса (резюме + требования стабильны внутри
подготовки) вход дешевеет заметно (кэш-чтение у провайдеров стоит долю от полной цены)
— но в текущем коде кэш не работает (I3, I4).

### Desktop-помощник, одно собеседование 60 минут

Тик каждые 12 с → 300 тиков. Каждый тик — `screen.extract` с кадром 1280×720
(~1,2 К токенов изображения) + резюме и требования (~2 К, из-за I1) + инструкция:
~3,5 К вход, 0,05 К выход. Плюс `assistant.hint` при найденном вопросе (~30% тиков):
~2,5 К вход, 0,1 К выход.

| Модель | Экстракция, 300 тиков | Подсказки, ~90 | Итого за час |
|---|---|---|---|
| Opus 5 | ~1,05 М вход → 5,3 $ + выход 0,4 $ | ~0,23 М → 1,1 $ + 0,2 $ | **~7 $** |
| Haiku 4.5 | ~1,1 $ | ~0,3 $ | **~1,5 $** |

Это на порядок дороже веб-сценария и упирается в неоптимальность, а не в природу задачи.

### Где деньги утекают зря (по коду)

1. Резюме и требования в каждом `screen.extract` (I1) — половина входа на каждом тике
   не нужна задаче.
2. Кадр без сравнения с предыдущим (I8): 70–90% тиков — экран не изменился.
3. Экстракция на дорогой модели: выделение вопроса из текста — задача для самой дешёвой
   модели или для локального OCR + регулярки.
4. Отсутствие кэша префикса (I3, I4): стабильные 2–3 К токенов оплачиваются полностью
   каждый раз.
5. Дедупликация по точной строке (I8): перефразированный вопрос → повторная подсказка.
6. `JSON.stringify(value, null, 1)` (`prompts.js:92`) — отступы и переносы в каждом
   запросе, +10–20% к объёму структурных секций.
7. Нет лимитов: один пользователь с включённым помощником на 8 часов — ~50 $ на Opus.
   Ни счётчика, ни отсечки, ни предупреждения (`desktop/README.md:131` это признаёт).

   `styles.css` и доменные функции.

### Потом

8. Кэширование префикса с проверкой `cache_read_input_tokens`.

### Не делать

- Не поддерживать три адаптера провайдеров, пока нет evals, которыми их можно

- Не расширять текущий `innerHTML`-макет новыми экранами: каждый новый экран — это

## 12. Вердикт

Перед вами хорошо оформленный кликабельный макет и два инженерных эскиза (слой модели и
Electron), написанных быстро и с честными пометками «не сверено», «не реализовано». Как
демонстрация замысла — цель достигнута. Как основа продукта — нет:

- frontend-подход исчерпан и его надо менять до подключения данных;
- слой модели не пережил бы первого реального вызова (B1, B2) и спроектирован вокруг
  одиночного запроса, а не диалога;
- desktop-модуль не снимает экран так, как нужно (B3), и несёт правовой риск, который
  код не может закрыть;
- инфраструктуры разработки нет вообще, а тесты закрепляют баги как норму.

Практический совет владельцу: считать сделанное **спецификацией** (экраны, состояния,
тексты, каталог переменных, слои контекста — всё это ценно как ТЗ) и начинать продукт
с фундамента: инструменты → бэкенд с прокси к модели → один провайдер с evals →
frontend на фреймворке. Desktop — отдельным решением после юридической проверки.
